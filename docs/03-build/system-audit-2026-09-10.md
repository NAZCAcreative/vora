# 전체 시스템 점검 — 2026-09-10

## 판정과 검증 범위

관리자 화면의 동작 검증과 서비스 전체의 운영 안전성은 다르다. 현재 결제·정산·출금·예약 및 일부 데이터 수정 권한에 운영 전 수정이 필요한 문제가 있다.

소스 코드, 연결된 Supabase의 실제 RLS·컬럼 수정 권한·트리거·제약조건·정산 실행 기록을 조회했다. 타입 검사는 통과했고 lint는 기존 경고 4건이다. `supabase/tests/admin_console.sql`, `supabase/tests/review_support.sql`은 실제 DB에서 통과했으며 모든 테스트 변경은 롤백했다. 이번 점검으로 앱 기능이나 운영 DB 설정을 변경하지 않았다. 실결제, 실제 송금, 로그인 제공자 통합, 동시 요청 부하 실험은 수행하지 않았다. 아래 악용 가능성은 실제 적용 권한과 코드를 근거로 판단했으며 운영 데이터에 공격성 변경을 실행하지 않았다.

## P0 — 운영 전 우선 차단

### 1. 결제사 승인 없이 결제 완료 기록 가능

근거: `src/lib/queries/bookings.ts:190`, `src/app/(main)/student/payment/page.tsx:85`, `supabase/migrations/0001_init.sql:482`.

`confirmPayment`는 브라우저가 전달하는 금액으로 payments에 succeeded를 INSERT하고 예약을 confirmed로 UPDATE한다. PG 승인 검증이 없다. 실제 DB에서도 본인 결제 INSERT/UPDATE 및 amount 수정 권한이 열려 있고, 결제 중복을 막는 예약별 고유 제약이 없다. 결제, 예약 확정, 쿠폰 사용은 별도 요청이라 중간 실패 후 재시도 시 중복 결제 기록이나 불일치가 생길 수 있다. 이는 실제 돈이 결제됐다는 의미가 아니라 DB가 결제됐다고 믿는다는 문제다.

조치: 사용자 직접 결제 성공 쓰기를 차단하고 서버에서 금액·쿠폰·예약 소유권을 계산/검증한다. 결제사 검증과 멱등 키를 도입하고 예약 확정·쿠폰 사용을 원자적으로 처리한다. 연동 전에는 테스트 결제임을 명시하고 운영 결제와 분리한다.

### 2. 출금 잔액 보호가 실제 DB에 없음

근거: `supabase/migrations/0009_withdrawal_balance_check.sql`, `supabase/migrations/0001_init.sql:527`, 실제 DB 카탈로그.

실제 DB에서 `to_regprocedure('public.check_withdrawal_balance()')`는 NULL이고 withdrawal_requests의 사용자 정의 트리거는 없다. 출금 INSERT는 본인 ID만 검증하며 양수·잔액 제한 제약도 없다. requested 상태 행의 금액 수정도 허용된다. 로컬 0009를 그대로 적용해도 INSERT만 검사하고 동일 회원 동시 요청에 대한 잠금이 없어 수정 우회와 경쟁 조건이 남는다.

조치: 출금 생성 전용 RPC에서 회원별 잔액 잠금·양수·정산 잔액·계좌를 검증한다. 사용자의 금액/처리 상태 직접 수정을 차단하고 취소 등 허용할 동작만 별도로 제공한다.

### 3. 정산 배치 실패와 실행 권한 과다

근거: `supabase/migrations/0005_settlement_batch.sql:5`, 실제 `cron.job_run_details`, 함수 실행 권한.

조회 가능한 최근 실행 기록 2026-08-10, 2026-08-17은 모두 실패했다. 오류는 `column reference "period_start" is ambiguous`다. 함수 매개변수와 테이블 컬럼 이름이 겹친다. SECURITY DEFINER 함수에 anon과 authenticated 모두 EXECUTE 권한이 있고 내부 관리자 검사가 없다. 현재 실행 오류가 권한 문제를 해소하지 않으므로, SQL만 고치면 외부 호출에 의한 정산 생성 위험이 남는다. 또한 금액 집계가 통화를 구분하지 않고 집계 결과를 곧바로 paid로 기록한다.

조치: 외부 실행 권한 회수, 매개변수명 분리, 중복·기간 겹침 방지, 통화별 집계, 정산 가능 잔액과 실제 지급 완료 의미 구분, 실패 감지와 재실행 정책을 함께 정비한다.

## P1 — 데이터 무결성·권한

### 4. 예약 중복·정원 초과를 DB에서 보장하지 않음

근거: `src/lib/queries/bookings.ts:51`, `supabase/migrations/0003_fix_lesson_sessions_rls.sql`, `0001_init.sql`의 lesson_sessions와 enrollments 정의.

기존 세션 조회→세션 생성→예약 생성을 별도 요청으로 수행한다. 같은 선생님·시작 시각의 세션 고유 제약이 없어 동시에 빈 결과를 받은 요청은 중복 세션을 생성할 수 있다. 기존 세션 재사용 시 teacher_lesson_id를 확인하지 않아 같은 시간의 다른 상품으로 연결될 수도 있다. 정원 검사는 클라이언트의 confirmed/completed 인원 스냅샷만 본다. 실제 DB는 로그인 사용자에게 임의 세션 INSERT를 허용하고 학생 본인에게 예약 상태 변경도 허용한다.

조치: 예약 전용 RPC로 상품·선생님·가능 시간·정원·무료 체험 자격을 확인하고 잠금 및 시간 중복 제약을 적용한다. 결제 대기 좌석 만료도 정의한다.

### 5. 리뷰·채팅 수정 권한이 필드 단위로 제한되지 않음

근거: `supabase/migrations/0001_init.sql:489`, `:513`, 실제 RLS 및 has_column_privilege 결과.

선생님은 본인에게 작성된 리뷰 행을 수정할 수 있어 답변뿐 아니라 학생의 본문·별점까지 수정할 수 있는 정책이다. 채팅 참여자는 상대방 메시지 행도 UPDATE할 수 있고 text 컬럼 권한이 있어 읽음 처리 외 내용 변경도 허용된다. 리뷰 작성은 본인 student_id만 확인하므로 실제 수강 완료와 중복 작성 제한도 DB에 없다. teacher_profiles의 rating_avg 직접 수정도 가능하다.

조치: 리뷰 작성/학생 수정/선생님 답변/채팅 읽음 RPC를 분리하고 필드별 권한을 최소화한다. 수강 이력과 리뷰 고유 제약, 집계 평점 직접 변경 방지를 추가한다.

### 6. 쿠폰 검증과 소비가 클라이언트에 의존

근거: `src/lib/queries/coupons.ts`, `src/app/(main)/student/payment/page.tsx`.

목록의 expiresAt을 결제 할인 함수가 검사하지 않는다. 결제 요청 후 별도로 쿠폰을 used로 바꾸며 사용자가 자기 쿠폰 상태를 직접 변경할 수 있다. 동시 사용, 재사용, 만료 쿠폰 할인에 대한 최종 DB 검증이 필요하다.

조치: 1번 결제 처리와 함께 서버에서 유효기간·활성 상태·소유권·사용 여부를 잠그고 검증한다.

## P2 — 사용자 흐름·규모 증가 대응

### 7. 알림 설정이 저장되지 않음

근거: `src/app/(main)/notification-settings/page.tsx:46`.

토글은 React 상태와 토스트만 변경한다. 새로고침하면 기본값으로 돌아가며 알림 생성 로직에 반영되지 않는다. 회원별 설정 DB와 알림 발송 단계의 설정 확인이 필요하다.

### 8. 일반 목록 페이징 및 채팅 조회 비용

근거: `src/lib/queries/chat.ts:15`, `:133`, `src/lib/queries/bookings.ts:228`, `src/lib/queries/settlement.ts`.

관리자 목록과 고객센터 목록은 DB 페이징을 하지만 일반 예약·결제·정산·채팅 목록은 범위 없는 SELECT다. 서버 반환 상한을 넘으면 누락 가능성이 있다. 채팅방 목록은 방마다 최근 메시지와 미확인 수를 순차로 추가 조회하여 방 N개당 1+2N개의 요청이 발생한다. 메시지는 오래된 순으로 조회하므로 상한 초과 시 최신 메시지가 초기 목록에 없을 수 있다.

조치: 일반 목록에도 페이지/커서를 적용하고 채팅방 요약은 집계 RPC 한 번으로 조회한다. 대화는 최신 메시지부터 가져오고 이전 내역을 추가 로딩한다.

### 9. 인증 상태 갱신과 이메일 인증 대기 처리 미흡

근거: `src/app/providers.tsx:26`, `src/stores/auth-store.ts:76`.

실제 세션 ID와 캐시 ID가 같으면 프로필을 새로 읽지 않는다. 다른 계정으로 세션이 바뀌었는데 fetchMe가 실패하면 이전 캐시가 남은 채 hydration을 완료할 수 있다. auth 상태 변경 구독도 없다. 이메일 인증이 필요한 설정에서는 가입 시 세션이 없을 수 있는데 바로 프로필을 읽고 isAuthenticated=true로 표시한다. 이는 관리자 DB 권한 획득을 의미하지 않지만 UI의 계정·로그인 상태를 잘못 표시할 수 있다.

조치: 세션 기반으로 스토어를 갱신하고 계정 전환 시 이전 사용자 데이터를 먼저 제거한다. 이메일 인증 대기를 별도 상태로 처리한다. 카카오·구글 연결 시 이 흐름을 함께 검증한다.

## 이번에 통과한 영역

- 박대건 고정 UUID 기반 관리자 권한, 표시 이름/role 변경에 의한 우회 차단.
- 관리자 목록 페이징·필터, 회원/수업/쿠폰/메모 변경과 이력 기록, 동시 수정 충돌.
- 선생님 심사·재심사·인증 동기화, 자기 인증 차단.
- 문의 접수 재시도 중복 방지, 답변/내부 메모 분리, 본인 조회와 비로그인/비관리자 차단.
